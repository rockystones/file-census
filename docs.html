qc.py — quick drive census, explained

One Python file (~330 lines, standard library only) that walks entire Windows drives and stores every file and folder's metadata in a SQLite database — without ever opening a file. This document explains what it calls, what it defines, and how the pieces run together.

1 · The libraries doing the heavy lifting

CallWhat it does for qc.py
os.scandir(dir) The workhorse. Lists one directory and yields an entry object per child. On Windows the operating system returns each child's metadata as part of the directory listing itself, so the follow-up entry.stat(follow_symlinks=False) is free — no extra system call, and crucially no file handle is ever opened. That is the source of the tool's "read-only, can't touch, can't block" guarantee.
stat fields From each entry qc.py reads: st_size, st_mtime_ns (modified) and st_birthtime_ns (created) as integer nanoseconds, st_file_attributes (the Windows attribute bit-field), and st_reparse_tag (set when the entry is a junction or symlink rather than a real file/folder).
os.listdrives() Returns the drive roots currently present (['C:\', 'D:\', …]). Python 3.12+ only — on older interpreters (3.11 Anaconda etc.) qc.py falls back to the Win32 GetLogicalDrives bitmask, one bit per existing drive letter.
sqlite3 The whole database engine, embedded, one output file. qc.py uses batch inserts (executemany), WAL journal mode (fast, safe), and one recursive SQL view that turns the stored parent/child tree back into full paths on demand.
ctypes → kernel32 Two tiny Windows API calls not exposed by Python directly: GetVolumeInformationW (volume label, filesystem name, serial number) and GetDriveTypeW (fixed / removable / remote / cdrom). Both are volume-level queries — again, no file opened.
shutil.disk_usageTotal and free bytes per drive, recorded with each scan.
tkinter Standard-library GUI. qc.py builds one small dialog from checkboxes (Checkbutton), a text field (Entry) for the catalog path, a save-file dialog (filedialog.asksaveasfilename), and warning popups (messagebox).
argparse / time / datetime Command-line parsing; time.monotonic() for the progress throttle and elapsed time; UTC timestamps in ISO form for the scan bookkeeping rows.

2 · What qc.py defines, and how values move

The functions

FunctionPurpose and data in/out
detect_drives() Asks Windows for every present drive and packages one dict per drive: {drive, type, label, fs, serial, total, free}. This list feeds both --list output and the GUI picker rows.
volume_info(root) ctypes wrapper returning (label, fs_type, serial_hex) for one drive root, or Nones if the query fails (empty CD drive, etc.).
pick_drives_gui(drives, explicit_db, auto_dir) Builds the dialog and blocks until the user acts. Returns a 3-tuple: the ticked drive letters, the catalog file path, and whether "allow catalog on a scanned drive" was ticked. Unless --db pinned a path, the catalog field live-updates the suggested name as drives are ticked, and stops the moment the user types or browses their own value. Cancel returns an empty drive list. Validation runs inside the dialog: no drives ticked, or a catalog placed on a drive about to be scanned, pops a warning instead of closing.
suggest_db_name(drives) The default catalog name: census_<letters>_drive_<YYYYMMDDHHMM>.sqlite — selected drive letters joined, plus local wall-clock minutes.
summarize_scan(con, scan_id) / write_summary(…) After scanning, one in-memory pass over the scan's rows rolls up each root-level entry: recursive size and file count, its major file types with counts, and subfolder counts per level. write_summary renders that plus the overall stats into a .txt preview next to the catalog (same name stem). The cap keeps the --top largest roots; display order then follows the sort spec (below), and omissions are noted.
parse_sort(spec) Parses the multi-key sort — "size:desc,type:asc,name:asc" (the default) — into ordered (key, descending) pairs. The GUI exposes the same thing as three priority slots (key + direction dropdowns); the table is then sorted by chained stable sorts, least-significant key first, so mixed directions compose correctly.
open_db(path) Opens/creates the SQLite file and applies the schema (all CREATE IF NOT EXISTS, so pointing at an existing catalog is a no-op and new scans append).
scan_drive(con, drive, skip_paths_cf) The core. Walks one whole drive and writes rows. Receives the open database connection and a small set of paths to skip (the catalog file itself plus its -wal/ -shm sidecars, so the census never contains its own output). Returns the new scan_id. Details in the walkthrough below.
main(argv) Glue: parse arguments → detect drives → choose GUI or CLI path → enforce the catalog-location guard → open the database → call scan_drive once per chosen drive → print where the catalog landed.
human(n) / iso_now() Cosmetics: byte counts as "10.4 GiB"; UTC timestamps as ISO strings.

The variables that carry the state

VariableRole
infos → drives infos is the detected-drive list; drives is the user's chosen subset, normalized to "X:" form. Everything downstream loops over drives.
args.db → db_path → skip The catalog location: default is census.sqlite beside the script, overridden by --db or by the GUI field. After the guard passes, the absolute path plus its two sidecar names becomes the skip set handed to every scan.
scan_id Primary key of the bookkeeping row created at scan start (status running) and finalized at the end (counts + status done / aborted). Every entry row carries it, which is how multiple scans — even of the same drive — coexist in one catalog.
next_id / parent_id Entry ids are assigned by the Python code, not by the database. Reason: a child row must store its parent folder's id, so the parent's id must be known before the database insert happens. Pre-assigning ids from a counter lets qc.py insert everything in large batches. The (parent_id → entry_id) chain is the folder tree.
stack The to-do list of the walk: tuples of (directory path, its entry id, depth). Starting with the drive root, each directory found is pushed; the loop runs until the stack is empty. An explicit stack (instead of recursion) means a million-deep tree can't overflow anything.
batch / err_batch Pending rows, flushed to SQLite every 5,000 via executemany + commit. Batching is why half a million rows insert in seconds.
n_files, n_dirs, n_bytes, n_errs Running counters shown in the progress line and written into the final scan row — so summary numbers are recorded facts, not re-derived.

The four things stored

Table / viewContents
scanOne row per drive per run: label, filesystem, serial, disk totals, start/finish times, final counts, status. The catalog accumulates history — re-scans of the same drive are new rows, enabling later comparison.
entryOne row per file or folder: parent_id (the tree), name, is_dir, size_bytes, modified/created times (integer nanoseconds), attribute bits, reparse tag, extension, depth. Full paths are deliberately not stored — storing each name once against a parent pointer kept a 642,000-row catalog at 73 MiB.
scan_errorDirectories/files that could not be listed (typically access-denied system folders), with the error text. The walk records and continues.
v_paths (view)A recursive SQL query that rebuilds X:\full\path strings from the tree when you ask for them — so the convenience of flat paths exists at query time without paying its storage cost. Always filter it by scan_id.

3 · Pseudo-code: the whole program on one screen

main:
    drive_infos = detect_drives()                     # letter, type, label, sizes
    if --list:  print drive_infos; exit

    if drive letters were passed on the command line:
        drives = normalize and verify them            # "e" / "E:\" → "E:"
    else:
        drives, db_path, allow = GUI dialog           # checkboxes + catalog field
        if user cancelled: exit

    if no db path chosen:
        db_path = census_<letters>_drive_<timestamp>.sqlite   # beside qc.py
    if db_path sits on any drive in drives and not allow:
        refuse and exit                               # the read-only promise

    con  = open_db(db_path)                           # creates tables/view if new
    skip = { db_path, db_path-wal, db_path-shm }      # never census our own output
    for drive in drives:
        scan_ids += scan_drive(con, drive, skip)
    write_summary(con, scan_ids, db_path.txt)         # stats + root-level structure table


scan_drive(con, drive, skip):
    scan_id  = insert scan row (status='running', label, fs, disk totals)
    next_id  = highest existing entry id + 1          # ids assigned in Python
    insert root row (name=drive, parent=NULL, depth 0)
    stack = [ (\\?\drive\, root_id, depth 1) ]        # \\?\ prefix = long-path safe

    while stack not empty:
        folder, parent_id, depth = stack.pop()
        children = scandir(folder)                    # may fail → scan_error, continue
        for child in children:
            meta = child.stat(follow_symlinks=False)  # free: comes with the listing
            id   = next_id;  next_id += 1
            if child is a folder:
                append row (id, parent_id, name, times, attr, depth)
                if not junction/symlink:              # reparse points recorded,
                    stack.push(child, id, depth+1)    #   never entered → no cycles
            else if child not in skip:
                append row (id, parent_id, name, size, times, attr, ext, depth)
            if 5000 rows pending: write them, commit  # executemany batch

        update progress line (throttled to 4/sec)

    write remaining rows
    finalize scan row: file/dir/byte/error counts, status 'done'
    print summary + top-10 extensions by bytes        # read back from SQLite
Why it's fast and safe, in one breath: the directory listing already contains every fact qc.py wants, so the tool is one long sequence of "list folder, remember children, push subfolders" — no file opens (nothing can be locked, modified, or triggered), no recursion (no depth limits), ids pre-assigned (everything batches), junctions never entered (no infinite loops), failures logged instead of fatal. 550,000 files → 68 seconds → one 73 MiB SQLite file you can query with plain SQL.
